# 小红书快消类种草批量文案与 QC 组件｜简短策划

## 1. 目标

先完成一条稳定、可复跑、可追踪的小红书快消类种草文案生产流程，再逐步优化提示词和内容质量。平台统一为小红书，内容统一为快消品种草；首版以“单个项目”为单位，生成模型和 QC 模型均通过 CLIPROXY API 调用，审核后的最终内容输出到飞书电子表格。

## 2. 项目建立

用户只需上传一份 Brief，也可直接粘贴 Brief 文字。系统提取文本后交给大模型，自动拆分成三块：

- `项目内容`：项目是什么、产品事实和基础素材是什么。
- `文案需求`：要写什么、写多少、以什么方式写。
- `QC 需求`：不能出现什么、最终按什么标准检查。

`项目内容`自动提取：

- 项目名称、快消品类、品牌、产品或 SKU
- 目标人群、消费痛点与典型使用场景
- 核心卖点、成分/规格/口味等产品事实及依据
- 价格或活动信息、可用素材与参考笔记

`文案需求`自动提取：

- 种草类型、生成数量、长度、人设、结构与语气
- 必须包含的内容和其他文案要求
- 默认语言、交付时间和负责人

模型 API 配置和飞书电子表格标识属于部署配置，不要求 Brief 提供，也不交给模型猜测；后续统一从 `.env` 加载，前端只显示连接状态，不提供凭证编辑入口。

`QC 需求`自动提取：

- 禁止宣称、禁用词和敏感表达
- 竞品提及边界、品牌表达边界和事实边界
- 项目通用 QC 和文案类型 QC
- 其他不通过条件及检查标准

模型需要为每个识别结果返回原文依据和置信度。原文没有提供的信息不补写；无法确定分类或存在冲突的内容进入“待确认”。用户可调整分类和字段，确认后才正式建立项目。

为保持首版轻量，支持 `.docx`、`.txt`、`.md` 和直接粘贴文本；PDF、Excel、图片或扫描版 Brief 的解析与 OCR 放到后续优化阶段。

项目建立后生成唯一 `project_id`，同时保存原始文字和用户确认后的结构化数据。后续文案要求、QC 规则、草稿、修改记录和飞书电子表格地址都归属于该项目。

### 可视化确认与修改

Brief 拆解完成后进入可视化确认页：

- 分区展示`项目内容`、`文案需求`、`QC 需求`和`待确认`。
- 每条信息以卡片或字段形式展示内容、原文依据和置信度。
- 用户可直接新增、编辑、删除，也可把识别错误的内容移动到其他分区。
- 缺失字段保持空白并突出提示，等待用户补充，不由系统生成默认内容。
- 项目配置使用明确的“保存并继续”，不实现复杂的实时版本系统；生成后的文案版本、AI 修改和审核事件必须留痕。

## 3. 输入文案要求（支持多种类型）

文案类型区域默认完全空白，首版不内置类型名称、模板或示例。类型只能来自用户补充或用户上传的文件，避免系统预设影响实际项目。

用户可以通过以下方式建立类型，参考案例与描述要求可以组合使用：

- 手动新增空白类型，填写类型名称、生成数量、标题与正文字数、人设、结构、语气和必须包含项。
- 像建立项目一样，在类型卡片中重新上传或粘贴一份该类型的 Brief。系统使用相同的文本提取、模型拆解和可视化确认流程，只把结果限定在当前类型。
- 粘贴或上传 1–5 篇完整爆款参考帖，由 AI 拆解后形成可编辑风格画像。

帖子类型的建立依据可以组合使用：`参考案例`和`描述要求`。用户可以只提供一篇爆款案例建立类型，也可以只描述要求，或在案例基础上补充标题方向、正文结构、人设、语气、场景和话题要求。

参考案例按完整帖子保存标题、正文和话题，可粘贴或上传 `.txt`、`.md`、`.docx`。AI 将案例拆解为可编辑的参考风格画像，包括标题钩子、开头方式、内容结构、段落节拍、信息密度、叙事视角、人设、语气、典型场景、卖点出现顺序、转折方式、结尾与标签策略，以及需要避免照搬的独特原句和来源事实。一篇即可建立类型，同一类型最多 5 篇，不做链接抓取。

类型另设`一定要有`与`一定不要有`，作为用户明确约束。它们优先于 AI 从案例推断的风格画像，但不能覆盖项目硬规则。用户没有单独填写类型 QC 时，系统把这两组约束转为可见、可编辑的默认类型 QC。

参考中的品牌、产品、价格、活动、功效和个人经历不得同步为当前项目事实。原案例全文必须完整保存；生成时把原案例、确认后的风格画像、描述要求和明确约束一并放入 Prompt，同时清楚标记当前项目事实是唯一事实来源、来源事实禁止继承、独特原句禁止照搬。原案例同时用于来源追溯和相似度检查。

类型也支持上传一个或多个要求/参考文件。文件先进入“未分类文件”区域，用户可新建类型并把文件移入，也可接受模型基于文件内容给出的分类建议。

每个类型以可编辑卡片展示，支持重命名、增删字段、附加或移除文件、调整文件归属和删除类型。模型只能依据 Brief 或用户文件填充内容；没有用户依据时保持空白。不同类型独立生成与 QC，但共享同一项目的产品事实和品牌要求。

类型 Brief 中出现新的项目级产品事实或与项目 Brief 冲突时，不得静默覆盖项目数据；系统生成“建议更新项目内容”或“事实冲突”提示，只有用户确认后才同步到项目内容。

首版只预留模板扩展口，不添加模板内容：

- 文案类型保留可选的 `template_id` 和 `template_version`，未使用模板时为空。
- 界面保留后续接入“从模板创建/导入模板”的位置，首版不显示可选模板列表。
- 用户当前手动建立的类型可在后续版本保存为模板，不改变现有类型数据结构。
- 模板只负责预填内容，导入后仍可编辑，并继续经过同一套用户确认和 QC 流程。

## 4. 项目 QC 要求

生成前，模型从项目 Brief 和各类型 Brief 的`QC 需求`中提取两级自动 QC，用户可在确认页补充或修改；生成后再进入人工个例 QC：

### A. 项目通用 QC

应用于项目内所有文案类型和所有条目，包括产品事实、品牌用词、禁用词、功效与成分宣称边界、小红书表达习惯、商业感控制和整体合规要求。

### B. 文案类型 QC

只应用于用户创建的某个 `copy_type`。类型未建立前不生成任何类型级默认 QC；建立后从 Brief、类型文件或用户输入中提取。

### C. 单独个例 QC

个例 QC 不在生成前配置，只在文案生成后出现。每条成稿拥有稳定的 `item_id`；AI QC 通过的条目可直接完成，异常项进入可编辑的人工审核状态，用户也可主动召回已生成条目进行人工检查。

人工个例 QC 提供两种修改方式：

- 直接修改：用户在标题、正文或话题标签中直接编辑文字。
- 定向 AI 修改：用户选中一段文字并右键打开对话框，输入修改方向；AI 只根据方向重写所选文字，用户决定是否采用结果。

进入人工审核后，由人工判断问题、修改结果和是否通过，AI 只承担按指令改写，不自动替用户做最终通过判断。

### D. 硬规则与软规则

- 硬规则：产品事实边界、禁止宣称、禁用词等，不可被文案类型或个例要求自动覆盖。
- 软规则：语气、结构、重点、表达偏好等，可由文案类型或个例要求调整。
- 下层要求与硬规则冲突时进入待处理状态，不自动覆盖；用户仍可强制通过，但状态必须标记为`强制通过`并记录全部遗留问题。
- 普通通过、强制通过和未通过是三个不同状态，飞书输出中必须保留审核状态和遗留问题。
- 存在未解决硬规则时不能标记普通通过，只能修复后通过、标记未通过或强制通过。
- 强制通过时遗留问题为必填，并自动带入当前尚未解决的 QC 问题；用户可以补充但不能清空。
- 文案类型软规则可以覆盖项目软规则；人工个例修改默认只影响当前文案，不形成持久规则，除非用户另行保存为规则。

## 5. 核心流程

```text
建立项目
  → 用户上传或粘贴 Brief
  → 提取 Brief 文本
  → 模型拆分：项目内容 / 文案需求 / QC 需求
  → 可视化展示拆解结果与待确认内容
  → 用户增删改、移动并确认三块内容
  → 文案类型保持空白，用户手动新增或上传类型文件分类
  → 每个类型可重新上传/粘贴类型 Brief 并可视化修改
  → 或提供一篇爆款参考文案，确认 AI 拆出的结构与风格画像
  → 用户确认各类型名称、要求、QC 和文件归属
  → 校验配置完整性
  → 调用模型 API 批量生成草稿
  → 项目通用与文案类型自动 QC
  → 整批重复度、覆盖度与一致性 QC
  → AI QC 通过项直接进入已完成（AI 自动通过）
  → 仅自动重写可修复的未通过项
  → 自动修改后再次 AI QC（限制重试次数）
  → 硬规则冲突、事实不确定、低置信度、相似度决策、重试耗尽或 API 异常进入人工审核
  → 用户直接修改，或选中文字后右键输入方向让 AI 定向修改
  → 人工定向修改完成后返回人工审核，不自动完成
  → 用户标记人工通过 / 强制通过并填写遗留问题 / 未通过
  → 只将已完成条目写入项目飞书电子表格的新子 Sheet
```

文案看板状态固定为：`待 AI QC → AI QC 中 → AI 修改中 → 待人工审核 → 已完成`。自动流程可从 AI 修改中返回待 AI QC；人工发起的修改从 AI 修改中返回待人工审核。修改次数只作为元数据，不建立“一轮/二轮”列。

## 6. QC 执行方式

采用“确定性检查 + 模型检查”组合：

- 程序规则先检查标题/正文字数、字段、关键词、禁用词、标签和格式，速度快且结果稳定。
- QC 模型再检查产品事实一致性、宣称边界、种草自然度、人设与场景、类型要求及整批重复度。
- 专项拦截凭空增加的产品事实、未经提供的亲身体验、夸张功效、过强广告腔，以及整批相同开头、结构和结尾。
- 对“爆款文案参考”建立的类型，额外检查生成稿与参考原文的标题、开头和全文相似度，避免直接改词式复刻或连续照搬独特表达。
- 每条规则返回：`通过/不通过`、原因、证据、修改建议和规则来源。
- 只把未通过项交给生成模型重写，避免整批重复生成和额外 API 成本。
- AI QC 全部通过后直接标记为`AI 自动通过`并进入已完成。
- 超过最大重试次数后停止自动处理，转为人工确认，防止循环调用。
- 进入人工个例 QC 后，AI 不再主动判断是否通过，只响应用户输入的定向修改指令。
- 人工输入的定向修改要求只用于本次改写，不纳入自动 QC 规则。
- 人工直接修改或采用 AI 修改后，重新运行确定性硬规则检查；最终是否普通通过或强制通过仍由用户决定。

## 7. 飞书电子表格输出

- 一个项目对应一份飞书电子表格，飞书只作为最终结果写入位置，不从飞书反向读取或管理人工修改。
- 每次确认输出都在同一电子表格中新增一个子 Sheet，使用运行时间和 `run_id` 命名；历史子 Sheet 不覆盖、不更新。
- 每个子 Sheet 写入：序号、`item_id`、文案类型、标题、正文、话题标签、完成方式、遗留问题和修改说明。
- 子 Sheet 默认只写入本次运行中已完成的条目，包括 AI 自动通过、人工通过和强制通过；未通过或仍待人工处理的条目保留在本地看板，不进入正式输出。
- “修改说明”来自人工直接编辑记录或用户输入的定向 AI 修改方向。
- 本地保存飞书 `spreadsheet_token`、本次 `sheet_id`、`run_id` 和访问链接。
- 同一次运行写入失败时，只重试对应子 Sheet 的创建或写入，不重新调用生成模型；本地已有 `sheet_id` 时继续使用，避免为同一次运行重复创建子 Sheet。
- 已输出后再次编辑并确认，视为一次新运行并创建新的子 Sheet；同一次运行的失败重试仍使用原 `run_id` 和 `sheet_id`。
- 飞书应用凭证、电子表格 API 权限和目标文件夹权限在部署时配置。
- 飞书开放平台能力由用户后续提供；在此之前只保留输出适配层和本地结果，不预设或写死凭证、权限与目标表格。

建议表格结构：

```text
项目电子表格
├─ 2026xxxx-运行01
├─ 2026xxxx-运行02
└─ 之后每次输出新增一个子 Sheet
```

## 8. 轻量方案

- 使用单体组件，不拆微服务。
- SQLite 是项目、规则、文案、QC、版本、审核和输出记录的唯一权威存储；JSON/CSV 只用于导出、测试夹具或诊断。
- 模型 API 使用统一适配层，首版兼容 OpenAI 风格接口，可替换服务地址、模型名和密钥。
- Brief 拆解与文案生成共用同一 API 适配层，不新增独立识别服务。
- 模板能力采用可插拔预填方式，首版仅保留字段和接口边界，不实现模板库。
- 生成模型与 QC 模型可分别配置，也可共用同一模型。
- 批处理采用受控并发、失败重试和调用日志，不引入消息队列。
- 飞书只负责把每次最终结果写入新的子 Sheet，过程数据仍保留在本地。

## 9. 首版交付边界

首版完成：项目及类型 Brief 上传/粘贴、文本提取、模型自动拆分、可视化编辑确认、空白文案类型创建、类型文件上传与分类、项目/类型自动 QC、异常项人工个例 QC、直接编辑、选中文字定向 AI 修改、硬/软规则、强制通过与遗留问题、标题/正文/标签批量生成、失败项定向重写、飞书电子表格新增子 Sheet、SQLite 持久化、结果导出，以及 API 调用成本和错误记录。

首版暂不做：内置模板及模板库、多项目并发管理、账号权限、复杂工作流编排、模型训练、自动发布到内容平台和深度文案优化。

## 10. 通过标准

- 用户只上传一份 Brief，即可获得`项目内容`、`文案需求`和`QC 需求`三组结构化结果。
- 同一句话同时包含多类信息时，可拆分后分别归入对应分类。
- 缺失信息不会由模型虚构，冲突或无法判断的内容进入“待确认”。
- 拆解结果可视化展示，用户能够增删改和调整分类。
- 文案类型初始为空，不出现任何预设类型、模板或默认内容。
- 首版不提供模板内容，但后续添加模板时无需修改现有项目和类型结构。
- 用户可以手动建立类型，也可以上传文件并调整文件分类。
- 每个文案类型都可以像项目一样单独上传或粘贴 Brief，并可视化确认拆解结果。
- 用户可以提供一篇爆款参考文案建立帖子类型；系统只抽取可编辑的结构与风格画像，不继承来源产品事实，生成稿还需通过与参考原文的相似度检查。
- 分类和类型配置必须经过用户确认，之后才能进入生成流程。
- 项目通用和类型 QC 在生成前配置并自动执行；AI QC 通过可直接完成，异常项在生成后进入人工个例 QC。
- 人工可以直接编辑，也可以选中文字后输入方向让 AI 单独改写。
- 硬规则不可被下层要求自动覆盖；强制通过必须保留状态和遗留问题。
- 同一项目可从配置完整运行到人工确认和飞书输出。
- 失败项可定向重写并复检，不重复生成已通过项。
- 同一项目的每次飞书输出都在同一电子表格新增一个子 Sheet，不覆盖历史结果。
- 每条最终文案都能追溯原始输入、生成结果、QC 结论和修改记录。
- 模型或飞书 API 异常时可安全停止、保留结果并单独重试失败步骤。
